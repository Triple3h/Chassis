# ADR-0003：管理面的特权边界 —— `ctx.settings` 只注入 internal 插件

- 状态：已采纳
- 日期：2026-09-14
- 相关：`docs/launcher-requirements.md` §3.4 / P2 / P5

## 背景

§3.4 要求"设置面板是 internal 插件"，它要读写：热键、开机自启、外观、历史上限、插件列表（启停/卸载/安装）、审计日志。

但 §8.6 的宿主 API 全表里**没有任何通用配置读写方法**——这是刻意的：普通插件不该有能力改宿主的配置或管理其它插件（否则权限模型形同虚设）。

## 决策

给管理面开一条**装配期注入**的特权通道，其余插件完全看不到：

| 项 | 决策 |
|---|---|
| 服务名 | `ctx.settings`（`SettingsService`） |
| 谁能拿到 | 插件 id 以 `internal-` 开头的插件（内核在 `createPluginContext` 时通过 `extra` 注入） |
| 怎么声明 | **不需要**在 `capabilities` 里声明（管理面不属于插件能力清单，也不出现在安装权限提示里） |
| 二次防护 | 服务内部再校验 `pluginId.startsWith('internal-')`，否则抛 `FORBIDDEN`（即使内核配置被改坏也不会越权） |
| 桥侧 | `ctx.settings.*` 由 `BridgeDispatcher` 单独分支处理，非 internal 插件调用直接 `FORBIDDEN` |
| 审计 | 所有 `ctx.settings.*` 调用照常落审计（P6 不因特权而豁免） |

对应 P2 的原文：「官方插件走同一套插件机制，可禁用、可卸载（**仅管理面除外**）」。

## 后果

**收益**

- 通用 API 表保持干净（不掺"读写宿主配置"），第三方插件无法通过任何已文档化的入口改宿主状态。
- 设置 UI 是普通 view 插件，可以用 SDK 写、可以热重载，不需要在启动台 UI 里写第二套设置界面。
- 审计不豁免，管理操作可追溯。

**代价**

- 多了一条不成文的规则：`internal-` 前缀 = 管理面。已在 `docs/architecture.md` 与代码注释中记录。
- `SettingsService` 的接口演进要同时改内核与 `@launcher/api`（可接受：只影响一个官方插件）。

## 备选方案与不采纳原因

| 方案 | 不采纳原因 |
|---|---|
| 把配置读写加进通用 API（`ctx.config`） | 任何插件都能改热键/清历史/装卸别的插件，权限模型失效 |
| 用新 capability `settings` 声明 | 会让"安装时展示能力清单"出现一个只对自家插件有意义的项；且普通插件声明它会被误认为合法 |
| 设置界面内置在启动台 UI 里 | 违反 §3.4（设置是 internal 插件）；且 UI 包会持续膨胀 |
| 用环境变量/文件约定让设置插件直接读 `<dataRoot>/config.json` | 绕过审计与校验，且插件会开始依赖内核内部文件布局 |
